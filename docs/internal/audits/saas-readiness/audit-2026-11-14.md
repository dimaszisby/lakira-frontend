### N17 · Auth (P1) — session revival redirects to the server's bind address behind a proxy

`src/app/api/auth/revive/route.ts:55` and `:65` build absolute redirect URLs from `request.url`.
In the production image, `request.url` is built from the address the server binds to
(`HOSTNAME=0.0.0.0`, `PORT=3000`, `Dockerfile:40-41`), not from the `Host` or `X-Forwarded-Host`
a reverse proxy sends; only `X-Forwarded-Proto` is taken. With the headers a proxy sets, revival
answered 307 to `https://0.0.0.0:3000/login?returnUrl=%2Fdashboard`. Inference from the same
line of code: a successful revival goes to the same host; only the failed one was probed in the
image. Under `next start --hostname 127.0.0.1` it is `localhost:3000`, and at `5e6beb9`, on Next
16.4.6, bound to `0.0.0.0`, it is `0.0.0.0` again.

Every page navigation with an expired access token goes through this route, and the backend issues
15-minute tokens. So on the VPS (ADR-0047), any user who pauses for a quarter of an hour and then
navigates is sent to an address the browser cannot reach. The edge gate's own redirects are
relative and unaffected. The unit tests build their requests on `http://localhost:3000`
(`src/app/api/auth/revive/__tests__/route.test.ts:42`), so they cannot see it, and no CI job puts
a proxy in front of the app.

**Recommended fix:** answer with a relative `Location` string, or build the URL on the configured
public origin (`resolveAppOrigin()`, `src/lib/env.ts:99`). Not by copying `src/proxy.ts`: it uses
the same `new URL(…, request.url)` pattern at `:97` and `:103`, and its `Location` came out
relative in every probe while the route handler's did not; add a test that sets
`Host` and `X-Forwarded-Host` and expects no bind address in the answer; probe the image as

### N18 · Forkability (P1) — a bootstrapped fork fails the unit gate

`src/__tests__/open-work-records.test.ts:24-34`, added on 2026-10-25 (#180), reads

### N21 · Error Handling (P2) — a backend outage during revival ends the session

`refreshAccessToken` returns `null` for an unreachable backend exactly as for a rejected token
(`src/lib/auth-refresh.ts:76-78`), and the revive route treats `null` as an ended session: it clears
both cookies and sends the user to `/login` (`src/app/api/auth/revive/route.ts:52-58`). Reproduced
with the backend stopped. The proxy, in the same state, answers 502 and keeps the cookies
(`route.ts:184-200`). So a backend restart, a deploy for instance, signs out every user whose
access token expired and who navigates during it, though their refresh token is still good.

**Recommended fix:** distinguish "unreachable" from "rejected" in the refresh result, and in the
first case answer with an error page or a retry rather than clearing the session.

### N22 · Forkability (P2) — private vulnerability reporting is off

`SECURITY.md:8` asks reporters to use GitHub's private vulnerability reporting, and the issue form
chooser links there (`.github/ISSUE_TEMPLATE/config.yml:4`). The repository has it disabled
(`GET /repos/…/private-vulnerability-reporting` answers `{"enabled":false}`), so the link offers no
form. `SECURITY.md:9-10` names a fallback, the maintainer's GitHub profile. A fork does not inherit
the setting either, and `docs/reference/issue-tracker.md`'s "In a fork" section does not mention
it.

**Recommended fix:** enable it in the repository's settings, and add it to the fork steps beside
`labels:sync`.

### N24 · Testing (P2) — nothing pins the loopback rule of ADR-0050

`src/services/api/api.ts:14-21` sends server-side calls to `/api/proxy` on `127.0.0.1`, so the
browser's address arrives as sent. With that line pointed at a public origin, all 1237 unit and 180
integration tests pass (V23f). The behaviour is correct today (section 2.2); a change that undid it
would put every signed-in user behind the reverse proxy on one rate-limit budget, which ADR-0049
calls a safe failure, and nothing would say so. `src/lib/__tests__/env.test.ts:135-143` tests
`resolveSelfOrigin` but not that the client uses it.

**Recommended fix:** a unit test on the client's server-side base URL.

### N25 · Code Architecture (P2) — the dashboard's time zone is fixed to Asia/Jakarta

`DEFAULT_TZ = "Asia/Jakarta"` (`src/features/data-visualizations/viz-helpers.ts:11`) is used by
the dashboard page, its content and every visualization, and `src/features/data-visualizations/api.ts:17`, `:26` and `keys.ts:8`,
`:15` fall back to the same string. Nothing reads the user's zone, so for a user anywhere else the
day buckets and "today" end at Jakarta's midnight. `docs/explanation/product-requirements.md:102`
names it as Lakira's default; `docs/reference/known-gaps.md` does not list it, so a fork inherits
it unannounced.

**Recommended fix:** read the browser's zone (or a user setting) and fall back to the constant;
until then, list it in `known-gaps.md`.
