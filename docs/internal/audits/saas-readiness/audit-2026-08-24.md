## 1. Verdict

**NOT FORK-READY — the frontend does not implement the tenancy model its own contract
declares.**

Seven of eight empirical gates are green and the codebase is, in craft terms, in good shape:
layer boundaries are enforced by ESLint across eight elements, 71 test suites pass, a CSP and
full security-header set ship in `next.config.ts`, the session token never touches JavaScript,
and the documentation tree is genuinely excellent. That is a better starting position than the
backend had at its own baseline.

What blocks it is structural, not cosmetic. The vendored contract
`docs/reference/api/lakira-backend-openapi.json` exposes `/organizations/{id}/members`,
`/organizations/{id}/invites`, `/memberships/{id}`, `/invites/accept`, and `/auth/switch-org`.
A grep of `src/` for any of those matches **only** the generated types file. There is no
organization concept in the UI, no switcher, no member list, no invite flow — and, critically,
none of the six `src/features/*/keys.ts` cache-key factories carry an org dimension. A forker
who wires this frontend to the multi-tenant backend it ships against gets a client that cannot
express which tenant it is acting for, and a cache that would serve one org's data to another
the moment a user belongs to two. That is the same defect the backend logged as N1/N2 on
2026-06-05, arriving from the opposite direction.

Alongside it: no `LICENSE` (criterion #4), no environment validation of any kind, no error
monitoring of any kind, no deployment configuration committed, and five auth-lifecycle flows
that exist in the contract and not in the app. The `api:spec:check` gate is **red right now**
— CI's `api-contract` job is failing on `dev` as of this audit.

Four gates pass vacuously and are graded as findings per ADR-003.

**Severity counts:** P0 = **8** · P1 = **21** · P2 = **8**.

# Gap entries

## 4.1 Auth & Session

### [P0] No token refresh

**Status:** MISSING · **Effort:** M
**What's missing:** `/auth/refresh` is in the contract; nothing in `src/` calls it. The session
cookie has a 7-day `maxAge` and no renewal path, so every session hard-expires.
**Why it matters:** a SaaS base whose users are silently logged out weekly, with no rotation,
has neither good UX nor a revocation story. The backend implements single-use rotation with
family revocation on reuse; the frontend ignores it entirely.
**Fix:** refresh on 401 inside the proxy handler, retrying once. Keep the refresh token in a
second httpOnly cookie; never expose either to JS.
**Evidence:** `docs/reference/api/lakira-backend-openapi.json` → `/auth/refresh`; no match in `src/`.

### [P0] No email-verification flow

**Status:** MISSING · **Effort:** M
**What's missing:** `/auth/verify-email` and `/auth/resend-verification` exist in the contract;
no route, page, or hook consumes them.
**Why it matters:** unverified-email signup is an open spam and account-takeover vector, and the
backend already gates on verification.
**Fix:** `/verify-email` route reading the token from `searchParams`, plus a resend affordance
on an unverified-account banner. Read `docs/internal/incidents/fix-searchParams-and-cookies-20251130.md` first.
**Evidence:** contract paths present; no match in `src/`.

### [P0] No password-reset flow

**Status:** MISSING · **Effort:** M
**What's missing:** `/auth/forgot-password` and `/auth/reset-password` exist; no UI.
**Why it matters:** an authenticated product with no self-service recovery is not shippable.
**Fix:** two routes under `(auth)`, reusing the RHF + Zod patterns in `src/features/auth/components/`.
**Evidence:** contract paths present; no match in `src/`.

### [P1] Middleware performs a presence-only cookie check

**Status:** PARTIAL · **Effort:** S
**What's missing:** `middleware.ts:14` reads the cookie and tests for existence. It never
decodes or validates the JWT, so an expired or garbage token passes the gate and fails
downstream as a confusing API error instead of a clean redirect.
**Why it matters:** the gate advertises protection it does not provide — the exact
documented-but-unenforced pattern in `.claude/lessons.md`.
**Fix:** decode and check `exp` at the edge (`jose` works in the Edge runtime). Signature
verification still belongs to the backend; expiry does not.
**Evidence:** `middleware.ts:14`.

### [P1] Session route accepts an unvalidated token

**Status:** PARTIAL · **Effort:** S
**What's missing:** `src/app/api/auth/session/route.ts` POST sets the session cookie from any
`{ token }` string in the request body, with no verification against the backend.
**Why it matters:** any script that can reach the route can plant a cookie value. It is not
directly exploitable today because the backend rejects bad bearers, but it makes the frontend a
willing oracle for cookie injection.
**Fix:** validate against `/auth/profile` before setting, or fold the whole thing into the
login route which already holds the verified token.
**Evidence:** `src/app/api/auth/session/route.ts`.

### [P1] Logout clears the cookie with mismatched attributes

**Status:** PARTIAL · **Effort:** S
**What's missing:** `src/app/api/auth/logout/route.ts:5` clears the cookie with `maxAge: 0` but
omits the `httpOnly`, `sameSite`, and `secure` attributes the two setter routes use.
**Why it matters:** attribute mismatch on clear is a classic source of a cookie that appears
deleted and is not, leaving a live session behind.
**Fix:** clear with the identical attribute set. Centralize the cookie options in one exported
object — which the Phase 2 brand constant should own anyway.
**Evidence:** `src/app/api/auth/logout/route.ts:5` vs `login/route.ts:15`, `session/route.ts:4`.

### [PASS] Token never reaches JavaScript

httpOnly cookie, bearer injected server-side by the proxy. `src/app/api/proxy/[...path]/route.ts:34`.

### [PASS] Protected routes gated at the edge

`middleware.ts` matcher covers `/dashboard`, `/metrics`, `/metric-categories`, `/account` with
a `returnUrl` round-trip.

## 4.11 Multi-Tenancy & SaaS Surface

### [P0] No organization concept in the UI

**Why it matters:** the frontend cannot express which tenant it is acting for. A forker wiring

### [P0] No organization switcher

### [P0] Cache keys carry no organization dimension

**Status:** MISSING · **Effort:** L
**What's missing:** all six `src/features/*/keys.ts` factories key on resource identity alone.
**Why it matters:** **this is the highest-risk item in the audit.** The moment an org switcher
exists, a user who belongs to two organizations will be served org A's cached payload while
acting as org B. The backend shipped exactly this defect (N1/N2, 2026-06-05) and had to patch
it same-day.
**Fix:** thread the active org id through every key factory _in the same change_ as the
switcher, never after. One integration test per feature asserting the key changes when the
active org changes. Read `docs/internal/incidents/fix-metric-detail-cache-stale-20251130.md`
first — this repo has already been bitten by cache-key assumptions once.
**Evidence:** `src/features/{auth,data-visualizations,metric-categories,metric-logs,metric-settings,metrics}/keys.ts`.
