# Lakira Frontend – Security Audit Log (Features / Components / App)

## Audit Metadata

- **Date:** 2025-11-21
- **Auditor:** Codex (LLM assistant)
- **Scope:** React components and feature modules under `src/features`, `src/components`, and `src/app` (UI, HOCs, pages, route handlers). Shared libs/services/styles were referenced only when needed for context.
- **Benchmarks Referenced:** OWASP ASVS v4.0.3 Level 2 (V1, V2, V4, V7, V10), OWASP Top 10 (2021), CIS Controls v8 (IG2 – 4, 6), NIST CSF (Identify/Protect), SLSA 1.

## Architecture Highlights (What Was Reviewed)

1. **Authentication UI & State** – Login/Register forms (`src/features/auth/components/`), auth React Query mutations, token storage helpers, and guard HOCs (`src/components/hoc/withAuth.tsx`, `requireToken.tsx`).
2. **Page Shells & Layouts** – App Router client pages in `src/app/(app)` and `(auth)`, `root layout`, and shared providers (`src/app/providers.tsx`).
3. **Feature Flows** – Metrics, metric categories, metric logs, and settings forms/lists (`src/features/**`). Focus on how data is validated, rendered, and mutated from the browser.
4. **Visualization Stack** – Chart.js wrappers (`src/components/ui/Visualization.tsx`, `src/features/data-visualizations/**`) for potential injection surfaces in tooltips/labels.
5. **Next.js Route Handlers** – `/api/auth/*` handlers managing login/logout cookies for parity with the client-only flows.

## Baseline Controls Observed

- **Typed validation on forms**: Login, registration, and metric forms use `react-hook-form` with `zodResolver` schemas (`src/features/auth/components/LoginForm.tsx`, `src/features/metrics/components/MetricForm.tsx`), aligning with ASVS V5 input validation expectations.
- **Centralized API client**: `src/services/api/api.ts` attaches Authorization headers, retries safe requests, and clears tokens on 401, reducing inconsistent per-feature implementations.
- **Auth guard HOC**: `src/components/hoc/withAuth.tsx` boots the user profile via React Query before rendering protected pages, preventing partial renders while auth is unknown.
- **UI accessibility cues**: Buttons, modals, and cards include `aria-*` labels (`src/components/ui/Modal.tsx`, `src/app/(app)/metrics/page.tsx`) improving defense-in-depth against clickjacking overlays.
- **Chart handling**: Visualization components treat metric series as escaped React text (no `dangerouslySetInnerHTML`), limiting XSS through data labels today.

## Findings & Recommendations

| ID              | Finding                                                                                                                                                                                                                    | Risk / Impact                                                                                                                                                                                                                                                                                              | Recommendation                                                                                                                                                                                                                                                                                              |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **FE-FEAT-001** | **Bearer token stored in `localStorage` and reused across all feature modules** (`src/features/auth/token.storage.ts:1-16`, `src/components/hoc/withAuth.tsx:37-58`, `src/services/api/api.ts:23-44`).                     | Tokens become accessible to any injected script and persist until manually cleared, violating ASVS V2.6 (token confidentiality) and enabling token exfiltration via XSS or malicious browser extensions.                                                                                                   | Transition auth to secure, HttpOnly cookies (Next route handlers already set `lakira_token` in `src/app/api/login/route.ts:1-21`); update Axios client to forward cookies instead of pulling from `localStorage`, and remove the storage helper once parity is achieved.                                    |
| **FE-FEAT-002** | **Auth enforcement happens solely on the client via HOCs wrapping client components** (`src/app/(app)/metrics/page.tsx:1-8`, `src/app/(app)/metrics/[id]/page.tsx:3-10`, `src/components/hoc/requireToken.tsx:9-31`).      | Because every protected page starts with `"use client"`, no server component or middleware verifies the session before rendering HTML. Attackers can hit the route handlers directly or disable client JS to bypass the guard, conflicting with ASVS V2.1/V2.3 expectations for centralized authorization. | Introduce a Next.js `middleware.ts` (or server layouts) that validates the HttpOnly cookie before serving `/app` routes, and ensure server components fetch data only after validation so SSR payloads never include protected data by default.                                                             |
| **FE-FEAT-003** | **Inline theme bootstrap script lacks nonce/hash support** (`src/app/ThemeScript.tsx:1-17`).                                                                                                                               | The script injects raw JavaScript via `<Script>{string}</Script>` requiring `unsafe-inline` in any CSP. This weakens CSP effectiveness for the entire app (ASVS V14).                                                                                                                                      | Move the logic into a tiny external file served with Subresource Integrity or leverage `next/script` with the `id` + `strategy` but pass code via `dangerouslySetInnerHTML` and supply a nonce through CSP headers. Alternatively, use `data-theme` initialization via CSS to avoid inline script entirely. |
| **FE-FEAT-004** | **“Add Dummy” metric creator is exposed in the production Metrics UI** (`src/app/(app)/metrics/page.tsx:205-221`).                                                                                                         | Any authenticated user can spam `useCreateMetricDummy({ count: 50 })`, potentially flooding the backend with dummy data or abusing a feature meant for development/testing. This violates least privilege & change-control expectations (CIS 4, ASVS V1).                                                  | Gate the action behind an environment flag or role check, remove it from production builds, and ensure the corresponding backend endpoint enforces authorization/quotas.                                                                                                                                    |
| **FE-FEAT-005** | **User-facing components surface raw API error messages** (`src/features/metrics/components/MetricForm.tsx:209-230`, `src/features/metric-logs/components/LogForm.tsx:83-139`, `src/components/layout/Sidebar.tsx:62-90`). | Server error strings (which may contain stack traces, IDs, or query details) are rendered directly in toasts/ErrorMessage components, enabling information disclosure (ASVS V1.7, OWASP A05).                                                                                                              | Sanitize outbound errors via `handleApiError` by mapping codes to friendly strings before displaying, and keep verbose diagnostics to telemetry/logs only.                                                                                                                                                  |

## Additional Notes / Next Actions

1. **Align on a single session mechanism**: Decide between HttpOnly cookies (preferred) or localStorage tokens, update guards/APIs accordingly, and document the flow in `threat-model.md`.
2. **Server-level protection**: After adding middleware/server layouts, retest each `/app` route to ensure unauthorized requests receive 302/401 before any component tree renders.
3. **Harden CSP**: Once ThemeScript is refactored, add CSP + other security headers to `next.config.ts` to mitigate XSS and clickjacking.
4. **Remove test-only controls**: Audit other feature modules for similar helper buttons (`createMetricDummy`, etc.) and hide them behind feature flags.
5. **Error-handling playbook**: Extend `handleApiError` to tag telemetry vs. user-safe messages and rewire UI components to consume the safe variant only.
